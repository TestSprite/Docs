## Overview

Every project gets its own detail page, the home base for its coverage map, test cases, runs, and settings. Open a project from <kbd>All Projects</kbd> and you land on its <kbd>Test Cases</kbd> (or, while the project is still being set up, on the stage it has reached or its Onboarding Checklist), with everything else one click away in the project's left nav.

<Frame>
  <img src="../../../images/project-overview.png" alt="A project's Insights page: trends and issues to fix" />
</Frame>

The header carries the project-wide actions: <kbd>Share</kbd> (invite someone to the workspace so they can open this project — see [Sharing a Project](/web-portal/admin/sharing)) and <kbd>Copy link</kbd>.

## The Left Nav at a Glance

<Frame>
  <img src="../../../images/ui-testing-side-nav.png" alt="The project left nav, grouped into Setup, Workspace, Analytics, Activity, and Project Settings" />
</Frame>

| Section | What it shows |
| :--- | :--- |
| <kbd>Insights</kbd> | Current status at a glance |
| <kbd>Test Coverage</kbd> | The visual map of features, use cases, and their statuses — see [Coverage Map](/web-portal/core/working-with-test/coverage-map) |
| <kbd>Test Cases</kbd> | The working list of every test, grouped by use case; API projects split into **Endpoint Tests** and **Integration Tests** — see [Managing Test Cases](/web-portal/core/working-with-test/managing-test-cases) |
| <kbd>Test Runs</kbd> | Every run of this project — watch one live or open its results and report |
| <kbd>Project Settings → General</kbd> | Rename or delete the project |
| <kbd>Sources</kbd> | The documents and crawled pages the plan is grounded in |
| <kbd>GitHub Action</kbd> | CI triggers for this project — see [GitHub Integration](/web-portal/integrations/github-integration) |
| <kbd>Environment</kbd> | Environment variables and per-environment configuration |
| <kbd>Notifications & Ticketing</kbd> | Where run results get announced and how failures become tickets |

Sections that have their own documentation page are summarized here only — follow the links for the full guides.

## Test Cases — the Working List

<Frame>
  <img src="../../../images/managing-test-case-overview.png" alt="The Test Cases list, grouped by use case with its toolbar" />
</Frame>

The <kbd>Test Cases</kbd> list is where day-to-day work happens. Each row shows the case's title, priority, latest status, and last run time; the toolbar holds <kbd>Add More Tests</kbd>, <kbd>Edit Test</kbd> (batch editing), and the run button, which doubles as an **execution-environment picker** when the project has environments configured. Select rows to run, delete, or add them to a [Test List](/web-portal/maintenance/test-lists) in bulk.

Everything about editing, adding, and deleting cases lives in [Managing Test Cases](/web-portal/core/working-with-test/managing-test-cases).

## Inside a Test Case

Clicking a row opens the test case as a **drawer** over the list — expand it to a full page when you need more room. The layout:

<Frame>
  <img src="../../../images/managing-test-case-edit-single.png" alt="A test case open — the definition on the left, Preview and Code on the right" />
</Frame>

**Left — the definition.** Priority, the test description (the prompt the run is judged against), and the step list. The case's name is shown as the heading and isn't edited in this view — rename it from the batch editor (<kbd>Edit Test</kbd> on the Test Cases list). <kbd>Edit steps</kbd> opens the step editor; the primary button is <kbd>Save & Run</kbd>, because an edited test only means something once it re-runs.

**Right — the evidence.** For UI tests, a <kbd>Preview</kbd> tab (the run's recording) and a <kbd>Code</kbd> tab. For API tests, the generated code plus its terminal output.

**Bottom — the run list.** The **Test runs** panel lists this case's past runs with status and date.

### Reading a failure

<Frame>
  <img src="../../../images/ui-testing-test-gen-failed-test.png" alt="A failed run — the recording above the Error, Cause, and Fix tabs" />
</Frame>

When a run fails, work through the evidence in this order:

1. **The verdict and error message** in the result panel — what the judge concluded, in plain language.
2. **The step trace** — which step failed, with the page state at that moment. For UI tests, the per-step replay is the richest view — see [Step-by-Step Walkthrough](/web-portal/core/ui/ui-step-by-step).
3. **The output** — terminal output for API tests, the recording for UI tests.
4. **The fix-suggestion prompt** — a ready-to-use prompt describing the failure for your coding agent; copy it into Cursor, Claude Code, or your IDE and let it drive the fix.

### Re-running after a change

- **Edited the steps?** Saving the step editor re-runs the case with the new steps immediately.
- **Edited the description or code?** <kbd>Save & Run</kbd> does both in one click (API tests: use <kbd>Regenerate</kbd> when the code itself must change).
- **Want everything re-checked?** Run the whole project from the Test Cases toolbar.

## Test Runs & Reports

<Frame>
  <img src="../../../images/ui-testing-report.png" alt="A run's Test Report — stat cards and the pass/fail/blocked donut" />
</Frame>

<kbd>Test Runs</kbd> lists every execution of this project. While a run is in flight you can watch the agent live, step snapshots included; afterwards, the run's report sums up pass/fail counts with AI-authored analysis of what broke and why, and can be **downloaded as a PDF** — an artifact you can hand to a PM or attach to a release note.

## Project Settings

<Frame>
  <img src="../../../images/project-setting.png" alt="Project Settings — project name, type, and extra instructions" />
</Frame>

| Action | Description |
| :--- | :--- |
| <kbd>Rename</kbd> | Change the project's name (autosaved) |
| <kbd>Share</kbd> | In the page header — adds someone to the workspace so they can open this project. See [Sharing a Project](/web-portal/admin/sharing) |
| <kbd>Export to GitHub</kbd> | In the project's row menu on <kbd>All Projects</kbd>. Push this project's generated test code to a GitHub repo, creating one for you if it doesn't have one yet. Uses your personal GitHub login, not the GitHub App (see [Exporting Test Code to GitHub](/web-portal/integrations/github-integration#exporting-test-code-to-github)) |
| <kbd>Delete project</kbd> | Removes the project with its tests, runs, and recordings. Available to workspace admins and the project's creator; asks for confirmation; not reversible |

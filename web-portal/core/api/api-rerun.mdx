## Three Rerun Surfaces

| Surface | What it does | When to use |
| :--- | :--- | :--- |
| <kbd>Single test rerun</kbd> | Re-execute one test | Confirm a fix on a specific failing test |
| <kbd>Run all</kbd> (batch) | Re-execute every test in the project | After API change, dep upgrade, or environment update |
| <kbd>Scheduled rerun</kbd> | Auto-run on cadence | Continuous monitoring of API health |

<Info>
**Auto-Heal is UI-only**, because UIs drift in ways HTTP APIs don't. For API tests, [Auto-Auth](/web-portal/core/api/auto-auth) is what keeps long-running schedules healthy by keeping tokens fresh.
</Info>

## Single Test Rerun

From a test's detail page, click **Run test**.

<Frame>
  <img src="../../../images/api-testing-rerun-open-rerun-single.png" alt="Rerunning one API test from its detail page" />
</Frame>

Most API tests consume variables from earlier tests in a chain. A normal rerun re-runs the producers first, getting fresh captures, then runs the consumer.

## Rerun All (Batch)

On the project's test list, **Run all** (top right) re-executes every test in the project.

<Frame>
  <img src="../../../images/api-testing-rerun-open-rerun-all.png" alt="Run all on the Test Cases toolbar, queueing every test in the project" />
</Frame>

## Scheduled Reruns

Schedules run on a cadence (hourly, daily, weekly, monthly). For API projects, each scheduled run rebuilds every chain, uses [Auto-Auth](/web-portal/core/api/auto-auth) when it's configured, and ends with Auto Cleanup so it leaves a clean environment. Set one up in [Test Schedules](/web-portal/maintenance/monitoring).

<Frame>
  <img src="../../../images/ui-testing-rerun-scheduled.png" alt="A schedule's page: execution trend, breakdown, and previous executions" />
</Frame>

## What Happens to Cleanup on Rerun

Every rerun (single, batch, or scheduled) ends with [Auto Cleanup](/web-portal/core/api/auto-cleanup). The DELETE chains are rebuilt from the records *the rerun* created, not the previous run's.

## Cascading: Rerun a Producer = Rerun Its Consumers

Rerunning a producer automatically reruns the tests that consume its variables, with the fresh values:

- Rerunning POST /users (a producer) → automatically reruns POST /orders, GET /orders/{id}, DELETE /orders/{id}
- Rerunning DELETE /orders/{id} (a leaf consumer) → only that test reruns; its upstream stays as-is

See [Dependency Chains](/web-portal/core/api/dependency-chains) for how producer/consumer relationships are identified.

## Rerun Outcomes

After a rerun, the test row shows the new outcome. The previous run is kept under <kbd>Test Runs</kbd>, so you can compare the two.

| Outcome on rerun | What it means | What you do |
| :--- | :--- | :--- |
| Was Failed → now Passed | Your fix worked, or the flake resolved | Move on |
| Was Passed → now Failed | Regression; either your fix broke something else, or the API changed | Investigate via test detail page |
| Still Failed (same error) | Fix didn't take | Refine more |
| Still Failed (different error) | You fixed one bug and uncovered another | Tackle the new error |

## Edge Cases & Troubleshooting

<AccordionGroup>
  <Accordion title="Rerun cascade goes deep — too many tests rerun">
    The producer you reran feeds many consumers across chains. To re-execute just one consumer, open that test and rerun it directly.
  </Accordion>
  <Accordion title="A test takes very long to rerun">
    Its producers depend on further upstream tests. A deep chain can make even a leaf test's rerun take several minutes.
  </Accordion>
  <Accordion title="Rerun shows a different result than the same code did the first time">
    Usually one of: a real flake in your API, captured state that changed between runs (a record was modified), or an auth token that expired between runs ([use Auto-Auth](/web-portal/core/api/auto-auth)).
  </Accordion>
  <Accordion title="The rerun button is disabled">
    The test is probably still Queued or Running. Wait until it shows Passed or Failed.
  </Accordion>
</AccordionGroup>

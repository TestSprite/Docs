title: "Quickstart"
description: "Walk through your first API project end to end, from project creation to a passing HTTP suite, in about 10 minutes."
---

By the end of this guide you'll have an API project that's been discovered, planned, generated as Python tests, and run against your live API, with every request and response captured. No code on your side.

<Info>
**Doing UI testing instead?** See the [UI Quickstart](/web-portal/core/ui/quickstart).
</Info>

## Step 1: Project Setup

From **All Projects**, click <kbd>New Project</kbd>. The form has three steps: **Basics**, **Access details**, and **Extra Context**. On **Basics**, set the **Test Type** to <kbd>Backend API</kbd>, then enter your **Base Endpoint** and a **project name**.

<Frame>
  <img src="../../../images/api-testing-quick-start-configure.png" alt="The Basics step of the New Project form, with Backend API selected, Base Endpoint, and Project Name" />
</Frame>

## Step 2: Review Discovered Endpoints

On **Access details**, click <kbd>Upload API docs</kbd> (OpenAPI, Swagger, Postman, or free-form docs). Discovery starts as soon as the file is uploaded, and your endpoints appear grouped by resource family in the **Set Up Your Tests** dialog.

<Frame>
  <img src="../../../images/api-testing-quick-start-discover-endpoint.png" alt="Discovered endpoint list" />
</Frame>

For each endpoint you can remove it (trash icon), fix its path (click the row), and set its **Authentication Type**: **Basic**, **Bearer**, **API-key**, or **None**. If discovery missed one, click <kbd>Add API</kbd>; with no docs at all, use <kbd>Add Endpoints Manually</kbd> on **Access details** instead.

When you're done, click <kbd>Save N endpoints</kbd> and continue to **Extra Context**.

## Step 3: PRD Upload & Extra Instructions

On **Extra Context**, choose <kbd>I have a PRD</kbd> and upload your **PRD** (**strongly recommended**; any product-spec document works). Optionally, add <kbd>Extra Instructions</kbd> to steer what gets tested, such as *"skip /admin"* or *"focus on the checkout flow"*. Then click <kbd>Create project</kbd>.

<Frame>
  <img src="../../../images/api-testing-extra-context.png" alt="The Extra Context step: Test Sources with the PRD upload, and Advanced Context with Test Files" />
</Frame>

<Tip>
**PRDs aren't only for UI.** They let TestSprite test the *intent* of each endpoint, not just its shape: "covers the order-placement scenarios your product supports", not just "covers `POST /orders`". Skip it for a quick demo; upload one for real coverage.
</Tip>

## Step 4: Feature & Use-Case Extraction

The new project opens on **Test Coverage**, with a flow graph of the features TestSprite found in your PRD and API docs and the use cases under each. Test cases are scoped to these use cases. Click <kbd>Regenerate from sources</kbd> to redo the analysis, for example after editing the file.

<Frame>
  <img src="../../../images/api-testing-quick-start-use-case.png" alt="Use-case flow graph on Test Coverage, extracted from the PRD" />
</Frame>

## Step 5: Review and Adjust the Plan

Click <kbd>Plan Tests</kbd> and TestSprite's testing agent plans the tests, grouped by use case and covering categories such as functional / happy path, authorization, error handling and edge cases, and (where relevant) boundary / load and security probes.

<Frame>
  <img src="../../../images/api-testing-quick-start-review-plan.png" alt="API plan review" />
</Frame>

Untick any tests that don't apply, edit titles or descriptions in natural language, and click <kbd>Run all</kbd>. On a first run, keeping everything selected is usually right; if a use case has more tests than you want, untick individual low-value ones rather than the whole use case.

## Step 6: Watch Tests Generate and Run

TestSprite generates a Python test per plan row, verifies each one, and runs them against your API. Each row shows <kbd>Planned</kbd>, <kbd>Running</kbd>, <kbd>Passed</kbd>, <kbd>Failed</kbd>, or <kbd>Blocked</kbd>. Tests that depend on each other run in the right order; see [Dependency Chains](/web-portal/core/api/dependency-chains).

<Frame>
  <img src="../../../images/api-testing-quick-start-review-run.png" alt="API tests executing" />
</Frame>

## Step 7: Review and Refine

Click any test to open its detail page: the generated **Code**, its **Stdout** (the HTTP calls and what your API returned), the **error trace** where an assertion failed, and an **AI cause-and-fix** suggestion. To change a test, edit its description and click <kbd>Regenerate</kbd>.

<Frame>
  <img src="../../../images/api-testing-quick-start-review-result.png" alt="API test detail page" />
</Frame>

The run's **Test Report** rolls up pass / fail / blocked counts with cause-and-fix highlights, ready to share with the team.

<Frame>
  <img src="../../../images/api-testing-quick-start-report.png" alt="Test Report summary view" />
</Frame>

## Step 8: Cleanup Runs Automatically

After the run, TestSprite removes the records your tests created (users, orders, sessions) so the next run starts fresh. The run's **Cleanup** tab shows what got deleted. See [Auto Cleanup](/web-portal/core/api/auto-cleanup).

## Step 9: Rerun and Schedule

To run again, use <kbd>Run test</kbd> on a single test or <kbd>Run all</kbd> on the **Test Cases** toolbar. See [Rerun](/web-portal/core/api/api-rerun), and set up [Auto-Auth](/web-portal/core/api/auto-auth) so tokens refresh before every run.

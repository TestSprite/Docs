## Overview

Before exploration can sign in anywhere, make sure login is configured for your project — see [Authentication (UI)](/web-portal/core/ui/ui-authentication).

Before writing any UI tests, TestSprite visits your live application and explores it feature by feature — opening real pages, attempting common user flows, signing in if you provided a test account, and recording what it could and couldn't reach. The test plan generated in the next step is grounded in **how your app actually behaves**, not just how it's described in your PRD.

This phase only runs for UI projects. Backend (API) tests skip exploration and go straight from configuration to plan generation.

<Note>
Some features may explore only partially. Even when exploration falls short, you can still continue to the test plan: TestSprite uses what was observed for explored features and falls back to your PRD/description for the rest.
</Note>

## What Exploration Does for You

<Tabs>
  <Tab title="What it is">
    A short, watchable run where TestSprite acts like a first-time user of your app. It opens your starting URL, identifies a list of features (e.g. *Sign Up*, *Dashboard*, *Checkout*), and walks through each one — clicking buttons, filling forms, navigating between pages — while you watch.

    Each feature is explored independently and in parallel, so a long flow doesn't block the rest.
  </Tab>
  <Tab title="Why it matters">
    Plans written from real behavior beat plans written from descriptions:
    - **Steps reference real selectors and copy** observed on your pages
    - **Edge cases come from real screens**, not assumed ones
    - **Auth flows match your actual login**, including unexpected redirects
    - **Features behind paywalls or gated by plan tier** are flagged honestly, instead of generating tests we can't run

    The result: fewer "this test doesn't match my UI" surprises during execution.
  </Tab>
  <Tab title="When it runs">
    Exploration runs automatically as soon as you click <kbd>Create project</kbd> on a UI project. It typically takes about **3 minutes** for an average app, though longer flows or large feature sets can take more.

    You don't have to babysit the run; you can leave the tab and come back. If exploration is still running when you return to the project, TestSprite picks up where it left off.
  </Tab>
</Tabs>

## What You'll See During Exploration

While exploration runs, the project's <kbd>Sources</kbd> page shows a live view headed **AI agent exploring your app** (or **AI agents exploring your app** when several are working):

    <Frame>
      <img src="../../../images/ui-testing-feature-explore-what-you-see.png" alt="The exploration view with Live Explore, Steps, Page Visited and Captured Pages labelled" />
    </Frame>

| Element | What it shows |
| :--- | :--- |
| <kbd>Progress counter</kbd> | With several agents, how many have finished (e.g. *"2/4 agents finished"*) |
| <kbd>Agent status</kbd> | Each agent's state: <kbd>Starting</kbd>, <kbd>Logging in</kbd>, <kbd>Exploring</kbd>, then <kbd>Done</kbd> or <kbd>Failed</kbd> |
| <kbd>Live browser preview</kbd> | Streams TestSprite navigating your app in real time |

When exploration finishes, TestSprite moves on to composing your coverage map on <kbd>Test Coverage</kbd>.

## Reviewing the Results

    <Frame>
      <img src="../../../images/ui-testing-feature-explore-review-result.png" alt="Sources page: Live Site Exploration with its status chip, recording, and Re-explore" />
    </Frame>

Exploration results live under **Live Site Exploration** on the project's <kbd>Sources</kbd> page. The **Explore your site** card carries a status chip (<kbd>Processing</kbd> while agents are working, <kbd>Ready</kbd> when they're done, <kbd>Failed</kbd> if the run didn't complete) and one card per exploration run, with its recording and the pages it captured. Click a run to open its recording and report.

## Adjusting Before Plan Generation

<Steps>
  <Step title="Reconfigure URL or credentials">
    If exploration was blocked because TestSprite couldn't sign in or reached a different URL than expected, open <kbd>Project Settings → Test Execution → Environment</kbd> and correct the environment's URL or test account.
  </Step>
  <Step title="Re-explore">
    Back on <kbd>Sources</kbd>, click <kbd>Re-explore</kbd> on the **Explore your site** card.
  </Step>
</Steps>

## Tips for a Good First Run

<AccordionGroup>
  <Accordion title="Provide a test account when possible">
    If your app requires sign-in, share a test account when you create the project. Both username and password are optional, but providing them dramatically expands what TestSprite can reach. Without credentials, exploration is limited to whatever's accessible without login.
  </Accordion>
  <Accordion title="Start from your real entry URL">
    Use the URL a real user would land on (e.g. your marketing homepage or app dashboard). Avoid deep links into specific tools — TestSprite uses the starting URL to discover the rest.
  </Accordion>
  <Accordion title="Use the extra-context field for hints">
    The optional context field is a good place for things like *"Skip the help center"*, *"Focus on the checkout flow"*, or *"The dashboard route is `/app/v2/home`"*. TestSprite uses these to guide both exploration and plan generation.
  </Accordion>
  <Accordion title="Don't worry about partial results">
    Plans generated from a mix of fully and partially explored features still come out solid — partial observations are real signal. The fallback path for couldn't-be-explored features is also well-trodden; you'll get a usable plan regardless.
  </Accordion>
</AccordionGroup>

UI Testing takes you from "here's my web app" to a regression suite that catches UI bugs without breaking on every minor refactor.

## Key Features

| Feature | Description |
| :--- | :--- |
| <kbd>Fast Setup</kbd> | Share your URL and, optionally, a test account |
| <kbd>Multiple Sign-In Methods</kbd> | Test account credentials, OTP (one-time password) login with a TestSprite-managed account (email and SMS), or SSO (single sign-on) such as Google {/* V3.1 (Sherry): TODO finalize wording */} |
| <kbd>Feature Exploration</kbd> | TestSprite's testing agent explores your live app so the plan reflects real behavior, not docs |
| <kbd>AI-Generated Test Cases</kbd> | Plans tailored to your real screens and flows; add, remove, or refine any case |
| <kbd>Live Test Preview</kbd> | Watch tests run in real time |
| <kbd>Step-by-Step Replay</kbd> | Every run records a video and per-step screenshots |
| <kbd>Auto-Heal</kbd> | When the UI drifts, TestSprite re-decides selectors against the live DOM instead of failing the test |
| <kbd>Natural Language Refinement</kbd> | Adjust any test in plain language, no code required |
| <kbd>Reusable Test Code</kbd> | Generated Python + Playwright tests, ready for CI/CD or regression suites |

<Tip>
**Each UI test is self-contained**: sign in, do the thing, assert. Unlike API tests, no data is passed between tests, so the work is in the single test (the page, timing, and absorbing UI change).
</Tip>

## Where Things Live

A UI project's sidebar is grouped into Setup, Workspace, Analytics, Activity, and Project Settings; see the [Test Detail Page](/web-portal/core/working-with-test/test-detail) for what each item does. Scheduling lives outside the project, under **Automation → Test Schedules**.

## Refining Tests in Natural Language

You can refine any test in plain language, by editing its description or asking in **Chats**. For example:

```text
Add a test that signs up a new user with an invalid email and confirms the inline validation appears.
```

## Testing an API Instead?

See [API Testing](/web-portal/core/api/api-testing). The flow mirrors this one; API projects discover and probe endpoints instead of walking pages, chain tests that depend on each other, and use [Auto-Auth](/web-portal/core/api/auto-auth) for token refresh rather than Auto-Heal. [Testing Lifecycle](/web-portal/concepts/testing-lifecycle) compares the two side by side.

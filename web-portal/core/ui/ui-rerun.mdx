## What Rerun Does

Rerun re-executes a UI test against your live app using the test's saved Playwright script. Same actions, same assertions, replayed from scratch. There are three places you can trigger a rerun from, plus **Auto-Heal**, which recovers tests when the page changed but the flow is fine. And when the test itself needs to change first, **Edit Steps & Rerun** lets you rewrite the steps and rerun in one motion (see [below](#edit-steps--rerun)).

This page is about plain rerun — what it does, where it lives, and how to use it. The Auto-Heal mechanics live on their own page.

## Quick Start

<Steps>
  <Step title="Open the test you want to rerun">
    From your project's **Test Cases** list in the sidebar, click into the test.
    <Frame>
      <img src="../../../images/ui-testing-rerun-open-test.png" alt="Test Cases in the sidebar, with a test row picked out of the list" />
    </Frame>
  </Step>
  <Step title="Click Run test">
    The button in the test's header is labeled <kbd>Run test</kbd> when the editor is clean, or <kbd>Save & Run</kbd> when there are unsaved edits. Replay starts immediately.
    <Frame>
      <img src="../../../images/ui-testing-rerun-rerun-single.png" alt="The Run Test button in a test detail page header" />
    </Frame>
  </Step>
  <Step title="Watch live or come back later">
    The test detail page updates in real time. You can stay and watch or navigate away and check the result later.
  </Step>
</Steps>

## Three Rerun Surfaces

### Single Test Rerun

From a test's detail page, click <kbd>Run test</kbd> (or <kbd>Save & Run</kbd> if there are unsaved edits) → done.

<Frame>
  <img src="../../../images/ui-testing-rerun-rerun-single.png" alt="Run button on a UI test detail page" />
</Frame>

### Rerun All (Batch)

The <kbd>Run all</kbd> button on the project's <kbd>Test Cases</kbd> toolbar queues every test in the project, useful after a refactor, dependency upgrade, or design pass.

<Frame>
  <img src="../../../images/ui-testing-rerun-open-rerun-selected.png" alt="Run all on the Test Cases toolbar, queueing every test in the project" />
</Frame>

### Scheduled Reruns

Schedules re-run your tests on a cadence (Hourly, Daily, Weekly, Monthly).

## Edit Steps & Rerun

{/* V3.1 (Sherry): new section — modify steps then rerun, per V3.1 item 4.9.5 */}

Sometimes the test is failing because the *test* is wrong — a step references a button that moved, or the flow gained a confirmation screen. Instead of rerunning the same broken script, open the step editor and fix the steps first.

<Frame>
  <img src="../../../images/ui-testing-step-edit-in-editor.png" alt="Edit steps & re-run dialog" />
</Frame>

<Steps>
  <Step title="Open the editor">
    On a test case's detail page, click <kbd>Edit Steps</kbd> beside the **Runtime steps** section — or hover a specific step and click its pencil icon (*Edit steps & re-run from here*) to start editing **from that step**.
    <Frame>
      <img src="../../../images/ui-testing-step-open-editor.png" alt="The Edit Steps button beside the Runtime steps section" />
    </Frame>
  </Step>
  <Step title="Rewrite from the pivot">
    If you opened the editor from a specific step, everything before it is **locked** — shown as-is and protected from editing. Everything from that step on is yours to rewrite: change a step's text, toggle it between <kbd>Action</kbd> and <kbd>Assert</kbd>, insert new steps with <kbd>Add step</kbd>, or delete steps.
  </Step>
  <Step title="Keep the pass criterion in sync">
    The <kbd>What counts as a pass</kbd> field at the top is what the run is **judged against** — not the steps. If your edits change what the test proves, update this too, or you'll get a run that does exactly what you asked and still fails.
  </Step>
  <Step title="Save & Re-Run">
    Click <kbd>Save & Re-Run</kbd>. The edited steps replace the test's definition (a new version appears in the version history), and the whole test runs immediately.
  </Step>
</Steps>

<Note>
**Locked ≠ skipped.** Every run starts from a fresh browser session, so locked steps are re-executed exactly as written — they're protected from *editing*, not from *running*.
</Note>

### Edit-and-Rerun vs. Plain Rerun

| | Plain Rerun | Edit Steps & Rerun |
|---|---|---|
| Test definition | Unchanged — replays the saved steps | Replaced — your edits become the new definition |
| Version history | No new version | A new version is created |
| When to use | Checking whether a failure reproduces, or whether the app was fixed | The failure is in the test itself — steps are stale or incomplete |

Edit Steps & Rerun is available for standalone UI test cases. It's not available for API tests, integration chains, read-only views (viewer role, historical versions), or while a run is already in flight.

## Edge Cases & Troubleshooting

<AccordionGroup>
  <Accordion title="Rerun started but the page didn't update">
    The test detail page subscribes to live status updates. If you don't see progress within a few seconds, refresh — the rerun is still happening server-side; this is just a live-update hiccup.
  </Accordion>
  <Accordion title="I want to keep my unsaved edits but rerun the saved version">
    The single-button design means clicking <kbd>Save & Run</kbd> always saves first. To rerun without saving, discard your edits via `Cmd`/`Ctrl`+`Z` or by reverting the editor, then click <kbd>Run test</kbd>. There is no "rerun-without-save-from-dirty-state" path by design: the dirty indicator (warning dot) signals you'd be running a different script than what's persisted.
  </Accordion>
  <Accordion title="Run all is greyed out">
    Either the project has no tests yet (still in plan-gen), or another project-level operation is in flight (e.g. an active run). Wait for that to complete; the button re-enables when the project is idle.
  </Accordion>
</AccordionGroup>

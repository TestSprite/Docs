The handful of terms the rest of the docs build on. Feature-specific terms, like auto-heal or auto-auth, are explained on their own pages.

## Workspace

The container everything else lives in: projects, tests, runs, and API keys. One is created for you at signup, and you can create more or be invited into others; the active one decides which projects you see. Every workspace works the same way, and each member has one role (Viewer, Member, Admin, or Owner). See [Workspaces](/web-portal/admin/workspaces) and [Members & Roles](/web-portal/admin/members-and-roles).

## Project

One application under test, or one slice of it (a single micro-frontend or API surface). A project is either **UI** (frontend) or **API** (backend) and holds its configuration, tests, and run history. Click <kbd>New Project</kbd> and tell the agent what to test; it proposes the project, and you create it. Until then it is a **Draft**. See [Setup](/web-portal/core/ui/agent-setup).

## Agent

TestSprite's agent is who you work with in the portal: it explores your app, writes and maintains the test cases, runs them, and judges what failed. It reads and drafts on its own, and asks before it changes your project or spends credits. See [Working with the Agent](/web-portal/getting-started/overview#working-with-the-agent).

## Session

One conversation with the agent, on one project. A project can have many sessions, listed in its sidebar; yours are private to you. Whatever a session saves to the project is shared with the team.

## Card

How the agent asks for your decision: a card above the chat box to create a project, save changes, apply a test plan, start a run, type a secret, or answer a question. One waits at a time.

## Exploration Notes

What the agent has learned about your app: its flows, how sign-in works, its test data, and what counts as correct. Every session on the project starts from them. See [Exploration & Notes](/web-portal/core/ui/agent-exploration#exploration-notes).

## Test Case

A single executable check. UI tests are multi-step user journeys (sign in, navigate, fill a form, assert); API tests are usually per-endpoint checks (call, then assert status, schema, and contract). Each has a title, a natural-language description, steps, and after each run a status: Passed, Failed, or Blocked. They live on the project's <kbd>Test Cases</kbd> page.

## Test Run

One execution of a set of tests. A run records a verdict per test, step-by-step screenshots and video (UI) or HTTP requests and responses (API), and a suggested cause and fix for each failure. Runs are listed on the project's <kbd>Test Runs</kbd> page.

## Test Plan

The project's test cases, grouped by use case. The agent proposes changes to it, which show on the **Plan** tab first; nothing changes until you apply them. See [Proposed Test Cases](/web-portal/core/ui/agent-plan).

## Environment

A named target your tests run against, such as dev, staging, or production, with its own URL, sign-in details, and variable values. Switching environments changes where a run goes without touching the tests. See [Environments](/web-portal/setup/environments).

## Test List

A reusable collection of tests, which can span projects: a regression suite, a smoke check, a release gate. A list has its own run history and is what you schedule. See [Test Lists](/web-portal/maintenance/test-lists).

## Test Schedule

A rule that runs a Test List automatically on a cadence, in your team's timezone. See [Test Schedules](/web-portal/maintenance/monitoring).

## Credentials vs. API Keys

Easy to mix up:

- **Credentials** are what TestSprite uses against *your* app: a test account for a UI project, or tokens and keys for an API project. They're stored encrypted and set per environment.
- **API keys** authenticate *you* to TestSprite, for the CLI and MCP Server. See [API Keys](/web-portal/admin/api-keys).

---
title: "Test Lists & Schedules"
description: "Run a saved group of tests with its environments, or schedule a list or project."
---

Use a test list for a selection you want to run again. A list can include tests from several projects and save a different environment for each project.

## Run a group of tests

Set `PROJECT_ID` and the two test IDs to values from `project list` and `test list`. The create command prints the ID to use for `LIST_ID`.

```bash
testsprite testlist create --name smoke --project-env "${PROJECT_ID}:staging"
testsprite testlist add "$LIST_ID" "$TEST_ID_1" "$TEST_ID_2"
testsprite run --testlist "$LIST_ID" --wait
```

To run a subset, supply its test IDs before or after the list selector:

```bash
testsprite run "$TEST_ID_1" --testlist "$LIST_ID" --wait
```

Use repeatable `--project-env <project-id>:<name>` on `testlist create` or `testlist update` to save bindings. Updating the bindings replaces the set, so include each mapping you want to keep. The list launch uses these bindings and rejects `--env`, `--local` and `--target-url`. A saved loopback address opens a [tunnel](/cli/core/local-apps) automatically. List launches default to a 600-second deadline. Server concurrency defaults to 10 (1–50), or 5 through a tunnel (1–10).

`testlist get "$LIST_ID"` lists the members and can include `lastRunId`. A launch can return several run receipts. Use a receipt's `runId` with `result list --run` and an individual `resultId` with `result get`.

If only some requested IDs belong to the list, the JSON field `notFound` lists the others. The CLI exits `4` for this partial match. With `--wait`, it polls the matched cases first, so a failure or timeout takes precedence. If every case conflicts, for example because every case is already running, the CLI can exit `6`. If the rate limit defers any cases, it can exit `7`. Both codes also apply without `--wait`.

## Run on a schedule

```bash
testsprite schedule create --name nightly --cron "0 3 * * *" \
  --target-type testList --target-id "$LIST_ID"
```

This schedule runs daily at 03:00 UTC. Set `--timezone` to use another time zone. Schedules start enabled and spend credits when they run. The CLI shows the estimated cost when the server supplies it. A plan without scheduling returns exit 13.

For a whole project, use `--target-type project --target-id "$PROJECT_ID"`. A project schedule follows the current default environment unless pinned with `--env staging`. A test-list schedule uses the list's bindings and rejects `--env`.

## Pause, change, or check a schedule

```bash
testsprite schedule get "$SCHEDULE_ID"
testsprite schedule update "$SCHEDULE_ID" --pause
testsprite schedule update "$SCHEDULE_ID" --resume
```

`schedule list` identifies a pinned project environment by name or shows `project default (inherits)`. View execution history in the Portal. A schedule targeting a loopback environment cannot reach your machine. The run is recorded as `blocked` with `failureKind: network` and incurs no charge. Start a local frontend run with `testsprite run --project "$PROJECT_ID" --local 3000` while your app is listening.

See [Test Lists](/web-portal/maintenance/test-lists) and [Test Schedules](/web-portal/maintenance/monitoring) for the Portal views.

---
title: "Running Tests"
description: "Launch a project, selected cases, or a saved list, then wait for the execution and find its results."
---

To run a project's tests and wait for the outcome, use its project ID. A **run ID** identifies an execution. Each test that runs in that execution gets its own **result ID**.

```bash
testsprite run --project "$PROJECT_ID" --wait
```

## Choose what to run

| Selection | Command |
| :--- | :--- |
| Whole project | `testsprite run --project "$PROJECT_ID" --wait` |
| Project cases whose names contain “checkout” | `testsprite run --project "$PROJECT_ID" --filter checkout --wait` |
| One or more named cases | `testsprite run "$TEST_ID_A" "$TEST_ID_B" --wait` |
| Saved test list | `testsprite run --testlist "$LIST_ID" --wait` |
| Selected members of a saved list | `testsprite run "$TEST_ID_A" "$TEST_ID_B" --testlist "$LIST_ID" --wait` |

Get case IDs from `testsprite test list --project "$PROJECT_ID"`. Positional IDs select tests. Named cases are grouped by project, so one command can return several run IDs. A saved list uses its own project and environment mappings. With no case or list selected, `TESTSPRITE_PROJECT_ID` supplies the default project.

For backend cases, the server includes declared dependencies. Use `--skip-dependencies` on named backend tests when their prerequisites already exist. For a project or group of cases, `--max-concurrency` controls how many tests the server can dispatch per execution.

## Wait for the verdict

On a public target, omit `--wait` to return after dispatch. Save the `runId` printed in the receipt. Add `--output json` for scripts.

```bash
testsprite run --project "$PROJECT_ID" --output json
```

`runs[].runId` identifies each execution. `results[]` can be empty at dispatch time. After waiting, `results[].resultId` identifies each available outcome and `summary` counts them. A full execution can gain integration results after its first cases pass. `--wait` follows the execution through completion.

## Resuming a run

```bash
testsprite run wait "$RUN_ID" --timeout 900 --output json
testsprite result list --run "$RUN_ID" --status failed,blocked
```

`run wait` resumes an existing execution without starting another. Supply several run IDs to wait for them under one deadline. To inspect a failed step or download its evidence, pass the row's `resultId` to `result get`. [Reading Results](/cli/core/reading-results)

## Ctrl-C and timeout

For an ordinary cloud run, Ctrl-C detaches and the run keeps executing. A timeout exits `7`. An incomplete wait can return `partial: true` with the receipts and results seen so far. For an automatic local tunnel, the CLI requests cancellation of its unfinished runs before closing the tunnel. [Cancelling a Run](/cli/core/cancelling-runs)

`--timeout` accepts 1–3600 seconds. The default wait is 600 seconds for public runs and 1200 for project or named runs through a tunnel. Saved-list launches and `run wait` default to 600 seconds.

## Run against a URL without creating an environment

To run a frontend case against a deployed preview, supply its public HTTP(S) URL. `--env staging` supplies staging's sign-in settings. A login tied to a different origin can be refused before dispatch. The CLI checks the target's reachability before launch.

```bash
testsprite run "$TEST_ID" --env staging --target-url https://preview.example.com --wait
```

For a backend project, select an environment whose base URL points at the API you intend to test. An ordinary backend launch uses that environment's URL and ignores a `--target-url` override. A CI pull-request preview can instead clone an environment at its preview URL. For a frontend app on your machine, use `--local <port>`. ## Exit codes

A completed wait exits `0` for a passing execution and `1` for a failed, blocked, or cancelled execution. A successful dispatch without waiting confirms acceptance. Errors such as insufficient credits or an unavailable service have their own exit codes. [Exit Codes](/cli/reference/exit-codes)

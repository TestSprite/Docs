Create an API key in the workspace that owns the projects you want to test. Runs draw on that workspace's balance. [API Keys](/web-portal/admin/api-keys)

## Signing in

From your repository, run setup and enter the key at the masked prompt. Setup verifies the key and installs the verification skill for the coding agents it detects. Use `testsprite setup --no-agent` for credentials only.

```bash
testsprite setup
testsprite auth status
```

For CI, supply `TESTSPRITE_API_KEY` through your CI secret store. Commands can use it directly. To run setup noninteractively with that key, use `testsprite setup --from-env --yes --no-agent`. Keep the secret in the environment so it stays out of shell history.

## Checking who you are

`auth status` shows the user, key ID, endpoint, API environment, and granted scopes. When available, `org:` shows the active workspace, plan, and role, and `org binding:` identifies the workspace tied to this key. Check the active workspace before running a suite. `usage` shows its balance.

```bash
testsprite auth status --output json
testsprite usage
```

## Profiles

Store keys for different workspaces in separate profiles. `--profile` chooses the profile for one command. `TESTSPRITE_PROFILE` sets it for a shell. The default profile is named `default`.

```bash
testsprite --profile checkout setup --no-agent
testsprite --profile checkout auth status
testsprite --profile checkout project list
```

Profiles are stored in `~/.testsprite/credentials` with mode `0600`. `TESTSPRITE_API_KEY` overrides the stored key even when you choose a named profile. If switching profiles shows the same workspace, check whether the variable is set. [Configuration](/cli/reference/configuration)

## Scopes

`auth status` lists the scopes granted to your key. Some operations need more than one. For example, waiting reads results, and local frontend execution also opens a tunnel.

| Scope | Examples |
| :--- | :--- |
| `read:me` | `auth status`, `usage` |
| `read:projects` | `project list`, `project get`, `project env list`, `project env get` |
| `read:tests` | `test list`, `test get`, `result list`, `result get`, `run wait`, `status` |
| `write:tests` | `plan`, `reply`, `apply`, `reject`, `stop`, `discard`, test-list changes |
| `write:projects` | `project create`, `project update`, `project env create`, `project env update` |
| `run:tests` | `run`, `run cancel` (also requires `read:tests`) |
| `read:schedules` | `schedule list`, `schedule get` |
| `write:schedules` | `schedule create`, `schedule update`, `schedule delete` |
| `run:tunnel` | Runs that open a tunnel, `tunnel start`, `tunnel list`, `tunnel status`, `tunnel stop` |

When a command returns `AUTH_FORBIDDEN`, check `details.requiredScope` and your workspace role. A workspace Admin or Owner can check your access. [Members and Roles](/web-portal/admin/members-and-roles)

## Signing out

```bash
testsprite --profile checkout auth remove
```

This removes the stored credentials for that profile from this machine. To revoke the key itself, use the API Keys page in the Portal. If your shell supplies the key, unset `TESTSPRITE_API_KEY` there as well.

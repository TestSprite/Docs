---
title: "Testing Local Apps"
description: "Plan frontend tests from local changes, then run them against your app through a TestSprite tunnel."
---

A TestSprite tunnel lets the cloud test runner use a frontend app on your machine. Start the app and keep it running until the execution finishes. Your key needs permission to run tests and open tunnels. [Authentication](/cli/core/authentication#scopes)

## A project for a local-only app

Create a frontend project. Copy its `projectId`, then create an environment for the port where your app listens.

```bash
testsprite project create --type frontend --name "Local checkout" --output json
```

```bash
export PROJECT_ID="your-project-id"
testsprite project env create "$PROJECT_ID" --name local-dev --local 3000
```

The hosted project agent cannot browse your localhost during planning. From the Git checkout, attach a diff and, if available, a requirements file with `--file`. These give it the expected behavior to plan from. To have it browse the app while planning, select a publicly reachable environment.

```bash
testsprite plan "Check that guest checkout shows the confirmation screen" \
  --project "$PROJECT_ID" --env local-dev --diff --steps
```

Review the proposed tests and their assertions. Once the plan matches what you want, save it. Then use a saved ID from `applied.tests` to run one case, or run the project against the local environment.

```bash
testsprite apply --output json
testsprite run --project "$PROJECT_ID" --env local-dev --wait
```

## Automatic tunnel

A saved loopback environment or an explicit local target opens a tunnel and implies waiting. For an existing frontend case, try one of these alternatives.

```bash
testsprite run "$TEST_ID" --env local-dev
testsprite run "$TEST_ID" --local 3000
testsprite run "$TEST_ID" --target-url http://localhost:3000
```

`--local` uses a loopback host and port. To select the exact host, use `--local-host localhost`, `127.0.0.1`, or `::1` with `--local`. `--target-url` accepts a loopback HTTP origin with an explicit port and no path, for example `http://[::1]:3000`. Choose one of `--local` or `--target-url` per run. Backend tests require a reachable API environment.

The CLI normally checks the listener before dispatch, waits for the verdict, and closes the tunnel on exit. An owned tunnel requests cancellation of its unfinished executions on Ctrl-C or timeout. `--no-wait` on an environment that requires an automatic tunnel is refused. A CLI-run loopback environment supports public access or username/password sign-in. [Cancelling a Run](/cli/core/cancelling-runs)

## Several tests

```bash
testsprite run "$TEST_ID_A" "$TEST_ID_B" --local 3000 --max-concurrency 3
testsprite run --project "$PROJECT_ID" --filter checkout --local 3000
```

Named or project launches share a tunnel and use a server dispatch limit per execution. For tunneled project or named tests the default is five, the maximum is 15, and the default wait deadline is 1200 seconds. Saved lists use their environment mappings, a separate tunnel cap of 10, and a default deadline of 600 seconds. The wait deadline covers the whole invocation.

## Long-lived tunnels

To reuse one tunnel across runs, start it in a separate terminal. It prints a client ID and stays in the foreground.

```bash
testsprite tunnel start --ttl 3600
```

Use that ID from a second terminal. The process that started the tunnel owns it. End that process with Ctrl-C when you finish.

```bash
testsprite tunnel status "$CLIENT_ID"
testsprite run "$TEST_ID" --local 3000 --tunnel-client "$CLIENT_ID"
```

## Tunnel limit

If a launch reaches the binding limit (exit `11`), run `testsprite tunnel list`. Reuse a connected binding or stop an unused one with `testsprite tunnel stop "$CLIENT_ID"`. Stopping a binding disconnects any run relying on it.

## Read a local result

The launch prints the same run and result IDs as a public run. Select the execution's failed or blocked cases, then download a result by its ID. To confirm a fix, keep the updated app running and launch the same case against the local environment again. [Reading Results](/cli/core/reading-results)

```bash
testsprite result list --run "$RUN_ID" --status failed,blocked
testsprite result get "$RESULT_ID" --out ".testsprite/results/$RESULT_ID"
```
